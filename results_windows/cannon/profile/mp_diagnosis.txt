Cannon multiprocessing: bottleneck diagnosis and optimisation
Machine: MacBook Air, Apple M5 (4 performance + 6 efficiency cores, no fan), 16 GB
Version 1 = first implementation (q = 4, 16 tasks); version 2 = q = 8, blocks >= 32.
Both used the sum(map(mul, ...)) kernel. The current code (version 3) follows the
revised statement: fixed q = 4 and an explicit i-j-k loop, so sections 1-8 describe
the earlier versions; sections 2 and 4 still explain the 16-task load imbalance.
=========================================================================================

1. Bottleneck of the sequential version (profile_seq.py; seq_512.txt, seq_1024.txt)
   M = 512 : _multiply_add 99.5 % of the run time (inner dot products 92.4 %), rest 0.5 %
   M = 1024: _multiply_add 99.8 % of the run time (inner dot products 95.8 %), rest 0.2 %
   Rest = skew, shifts, NumPy -> list conversion, joining C: O(M^2) work.

2. Where the time of multiprocessing version 1 went (one multiplication, per-task timestamps)
   M     p   total(s)  main-process serial work  first task starts  data pickled  worker idle  list conversion
   128   6    0.010    0.3 ms                    0.3 ms               1.1 MB       16.5 %      1.2 % of task time
   512   6    0.422    1.7 ms                    0.8 ms              17.3 MB       11.4 %      0.5 %
   1024  4    3.908    5.8 ms                    3.8 ms              69.0 MB        1.3 %      0.2 %
   1024  5    4.241    6.1 ms                    4.0 ms              69.0 MB       16.4 %      0.2 %
   1024  6    3.787    6.0 ms                    4.0 ms              69.0 MB       15.2 %      0.2 %
   2048  6   30.120   33.7 ms                   11.7 ms             276.0 MB       10.4 %      0.1 %
   Main-process serial work = building the tasks + joining C. Worker idle = share of
   p x makespan in which a worker had no task.
   -> Serial work, data transfer and conversion stay below 1 %. The loss is load
      imbalance: 16 equal tasks do not divide over 5 or 6 workers (idle 10-16 %),
      while 4 workers are balanced (idle 1.3 %).

3. Hardware effect: speed of the kernel on one core while other cores only spin
   (spinners do no memory traffic)
   other busy cores:     0      1      3      5      0 (after)
   ns per multiply-add: 12.3   12.8   15.2   18.5   12.2      (512-wide blocks)
   -> each core slows down ~1.5x when 6 cores are busy: clock/power management of the
      fanless laptop, not the code. The same multiplication (M = 2048, p = 6, q = 4)
      took 30.1 s on a cool machine and 38-47 s after sustained load.

4. Task granularity: one multiplication with version 1's layout, q varied (seconds)
                 q = 4 (16)   q = 6 (36)   q = 8 (64)   q = 16 (256 tasks)
   M=1024, p=4     4.367        4.336        4.477        4.834
   M=1024, p=5     4.650        4.429        4.298        4.584
   M=1024, p=6     4.027        3.864        4.026        4.217
   M=2048, p=5    39.409       37.142       35.785       37.867
   M=2048, p=6    38.391       37.094       37.375       38.727
   data pickled at M=2048: 276 / 404 / 532 / 1044 MB
   -> 36-64 tasks balance better; 256 tasks cost more (transfer volume grows with q,
      shorter dot products make the kernel less efficient).

5. Small matrices: speed-up over sequential for each q (p = 6, median of 15 runs)
   M       q = 1   q = 2   q = 4   q = 8   q = 16
   16      0.40    0.41    0.17    0.04    0.01
   32      0.82    1.16    0.89    0.24    0.04
   64      0.93    2.27    2.23    1.33    0.26
   128     0.98    3.02    2.99    2.59    1.44
   256     0.98    2.99    3.22    3.01    2.42
   512     0.99    2.87    3.20    3.15    2.55
   -> tasks on blocks narrower than about 32 cost more to dispatch than they compute:
      CANNON_MIN_BLOCK = 32 gives q = 1, 1, 2, 4, 8, 8 for M = 16 ... 512.

6. Version 1 vs version 2, alternating runs (positive = version 2 faster)
            p = 2    p = 3    p = 4    p = 5    p = 6
   M=2048   +4.9 %   +5.5 %   +3.6 %  +11.0 %   +7.9 %
   M=1024   -0.2 %   +3.7 %   -4.5 %   +9.8 %   +1.8 %
   -> the gain is largest where 16 tasks divided worst (p = 5, 6, 3). At M = 1024 with
      p = 4 the 16 tasks were already balanced, so the smaller blocks only cost ~4 %.

7. Full benchmark, speed-up over G0..G9 (cumulative, Table D-3.2)
                            p = 1   p = 2   p = 3   p = 4   p = 5   p = 6
   version 1 (commit 770010e) 0.98    1.52    1.82    2.14    2.22    2.65
   version 2 (current)        1.01    1.70    2.07    2.40    2.65    2.82
   Sequential total: version 1 1303.3 s, version 2 1291.2 s, so the q = 8 grid does not
   slow the sequential version down. The two full runs were made at different times and
   thermal states, so part of the difference is run-to-run variation; section 6
   (alternating runs) is the controlled measure of the optimisation itself. The p = 1
   overhead (1-2 %) is below this variation, hence S_1 = 1.01 in version 2.

8. Note on the sequential measurement of the version-2 run
   The first sequential run (raw/seq_first_attempt.json) took 148-155 s per group, ~17 %
   slower than the p = 1 run that followed (127-131 s, same arithmetic in one worker)
   and than version 1 (124-133 s). Power (AC, Low Power Mode off), process priority and
   competing CPU load were checked without finding a cause. The sequential part was
   therefore re-run after the multiprocessing runs (raw/seq.json, 128.7-129.6 s per
   group) and the tables use the re-run. This departs from the protocol's order
   (sequential first) and is stated in the report.
